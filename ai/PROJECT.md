# PROJECT

## 기술 스택

- Language: TypeScript
- Runtime: Node.js
- Framework: Express
- ORM: Prisma
- RDBMS: MySQL
- API Docs: Swagger
- Test: Vitest, Supertest
- Auth: JWT
- AWS: S3, EC2, RDS
- CI/CD: Docker, GitHub Actions

이 스택을 벗어나는 라이브러리나 패턴(NestJS 데코레이터 스타일, TypeORM, MongoDB 등)을 임의로 도입하지 않는다.
새 의존성이 필요하면 먼저 제안하고 승인을 받는다.

## 프로젝트 설명

### 서비스 개요

네일내일은 사용자가 원하는 네일 디자인 이미지, 시술 조건, 가능한 일정을 등록하고 주변 네일샵의 견적을 받아 가격·거리·예약 가능 시간을 비교한 뒤 예약을 확정하는 서비스다.

서버는 사용자와 네일샵 사이의 견적 요청, 샵 응답, 견적 비교, 예약 확정 흐름을 관리한다. MVP에서는 사진 기반 견적 요청부터 예약 완료까지의 핵심 흐름을 우선 구현한다.

### 사용자 유형

- **사용자**: 디자인 이미지를 등록하고 견적을 요청하며, 도착한 견적을 비교해 예약한다.
- **네일샵**: 전달받은 요청 조건을 확인하고 시술 가능 여부, 가격, 가능 시간 등의 견적을 제출한다.

### 핵심 사용자 흐름

```text
홈
  -> 사용자 견적 요청
  -> 디자인 이미지 최대 3개 업로드
  -> 시술 정보 및 가능 일정 입력
  -> 견적 탐색 범위 선택
  -> 요청 내용 확인 및 견적 요청
  -> 샵별 견적 수신 및 비교
  -> 샵 견적 상세 확인
  -> 예약 시간 선택
  -> 예약 확정
```

### 기능 우선순위

- **P0**: MVP에서 반드시 구현해야 하는 핵심 기능
- **P1**: 서비스 완성도를 높이는 후속 기능
- **P2**: 고도화 단계에서 검토할 기능

#### P0 — MVP

- 홈에서 현재 위치와 진행 중인 견적 요약 조회
- 디자인 이미지 업로드 및 견적 요청 정보 입력
- 탐색 범위에 따른 요청 대상 샵 선정 및 견적 요청 전송
- 견적함에서 요청 진행 상태와 샵별 응답 조회
- 가격, 예약 가능 시간, 거리 기준의 견적 비교
- 샵 견적 상세 조회 및 예약 시간 선택
- 예약 확정과 확정·지난 예약 조회
- 네일샵의 구조화된 견적 응답 제출

#### P1 — 후속 기능

- 디자인 피드와 디자인 상세
- 견적 정렬 필터, 가격 상세, 샵 코멘트
- 예약 변경 및 취소
- 디자인·매장 찜
- 견적·예약 알림과 알림 설정
- AI를 이용한 요청사항 메시지 보정

#### P2 — 고도화 기능

- 인스타그램 링크를 이용한 견적 요청
- AI 디자인 분석
- 디자인 매칭도, 유사 작업물, 샵 응답률 기반 추천
- 최저가 중심 탐색
- 결제 및 예약금
- 샵 관리자, 프로모션 및 광고 기능 고도화

### 핵심 도메인

| 도메인 | 책임 |
|---|---|
| 사용자(User) | 프로필, 위치, 알림 설정 관리 |
| 네일샵(Shop) | 샵 기본 정보, 위치, 영업 및 예약 가능 정보 관리 |
| 디자인(Design) | 사용자 업로드 이미지와 피드 디자인 관리 |
| 견적 요청(Estimate Request) | 시술 조건, 가능 일정, 탐색 범위, 요청 상태 관리 |
| 견적 응답(Estimate Response) | 샵의 시술 가능 여부, 가격, 가능 시간, 코멘트 관리 |
| 예약(Reservation) | 선택한 견적과 시간 슬롯 기반 예약 및 상태 관리 |
| 찜(Favorite) | 사용자가 저장한 디자인과 매장 관리 |
| 알림(Notification) | 견적과 예약 상태 변경 알림 관리 |

### MVP 핵심 정책

#### 견적 요청

- 디자인 이미지는 최소 1장, 최대 3장으로 제한한다.
- 견적 요청에는 시술 부위, 제거 유형, 가능한 일정, 탐색 범위를 반드시 포함한다.
- 예상 가격 범위와 추가 요청사항은 선택 입력으로 둔다.
- 가능한 일정은 요청 시점부터 7일 이내로 제한한다.
- 시간대는 `오전(08:00~12:00)`, `오후(12:00~18:00)`, `저녁(18:00~22:00)`, `상관없음`으로 구분하며 기본값은 `상관없음`으로 설정한다.
- 시술 부위는 `손 네일`, `패디`, `손+발` 중 하나를 선택한다.
- 제거 유형은 `연장 제거`, `젤 제거·파츠 있음`, `젤 제거·기본`, `없음` 중 하나를 선택한다.

#### 탐색 범위

| 옵션 | 대상 샵 수 | 기준 | 우선순위 |
|---|---:|---|---|
| 가까운 5곳 | 5 | 이동 거리가 가까운 샵 우선 | P0 |
| 균형 추천 8곳 | 8 | 거리, 가격, 응답 가능성을 균형 있게 반영 | P0 |
| 넓게 비교 10곳 | 10 | 탐색 범위를 넓혀 더 많은 견적 확보 | P0 |
| 최저가 탐색 10곳 | 10 | 낮은 가격 가능성이 높은 샵 포함 | P2 |

기본 탐색 옵션은 `균형 추천 8곳`으로 설정한다.

#### 샵 견적 응답

- 샵은 요청의 디자인 이미지와 시술 조건을 확인할 수 있어야 한다.
- 시술 가능 여부, 예상 가격, 예약 가능 시간은 필수로 입력한다.
- 예상 소요 시간, 제거비 포함 여부, 코멘트는 선택 입력으로 둔다.
- 사용자에게는 샵명, 가격, 가능 시간, 거리 정보를 기본 제공한다. 평점, 리뷰, 가격 상세 등은 후속 범위에서 제공한다.

#### 예약

- 사용자는 샵이 제안한 예약 가능 시간 슬롯 중 하나만 선택할 수 있다.
- 예약은 하나의 견적 응답과 하나의 시간 슬롯을 기준으로 확정한다.
- 예약 확정 후 샵명, 날짜, 시간, 주소, 가격, 디자인 정보를 조회할 수 있어야 한다.
- 예약 변경과 취소는 P1 범위로 둔다.

### 주요 상태

구현 시 상태 값은 문자열을 직접 비교하지 않고 enum 또는 상수로 관리한다.
실제 명칭은 API·DB 설계 시 확정하되 다음 상태를 표현할 수 있어야 한다.

- **견적 요청**: 작성 중, 요청 완료, 응답 대기, 응답 도착, 마감
- **견적 응답**: 응답 대기, 시술 가능, 시술 불가, 제출 완료
- **예약**: 예약 확정, 변경 요청, 취소, 완료

동일 견적 응답의 중복 제출과 동일 시간 슬롯의 중복 예약을 방지해야 한다.
예약 확정처럼 경쟁 상태가 발생할 수 있는 작업에는 데이터베이스 트랜잭션과 제약조건을 함께 사용한다.

### 공통 오류 정책

다음 상황은 공통 에러 응답 형식과 명확한 에러 코드로 처리한다.

| 상황 | 사용자 메시지 |
|---|---|
| 사진 업로드 실패 | 사진을 업로드하지 못했어요. 다시 시도해주세요. |
| 위치 정보 없음 | 주변 샵을 찾기 위해 위치가 필요해요. |
| 필수값 미입력 | 필수 정보를 입력해주세요. |
| 견적 요청 실패 | 견적 요청을 보내지 못했어요. 다시 시도해주세요. |
| 예약 실패 | 예약을 완료하지 못했어요. 다시 시도해주세요. |

### 서버 구현 원칙

- 이미지 파일은 AWS S3에 저장하고 DB에는 외부에 직접 노출하지 않는 object key와 필요한 메타데이터만 저장한다.
- 위치 기반 샵 탐색은 거리 계산 기준과 최대 탐색 반경을 API 설계 전에 명확히 정한다.
- 가격은 부동소수점이 아닌 정수 단위로 저장하며 통화는 원화(KRW)를 기본으로 한다.
- 날짜와 시간은 서버와 DB에서 일관된 기준으로 저장하고, 클라이언트 응답에는 타임존을 명확히 적용한다.
- 목록 API에는 페이지네이션을 적용하고 정렬 기준을 허용 목록으로 제한한다.
- 견적 요청, 견적 응답, 예약의 생성·상태 변경 API에는 인증과 리소스 소유권 검증을 적용한다.
- 알림 발송 실패가 견적 또는 예약 트랜잭션 자체를 실패시키지 않도록 핵심 데이터 변경과 알림 처리를 분리한다.
